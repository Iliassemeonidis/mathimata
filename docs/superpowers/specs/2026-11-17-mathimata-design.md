# Mathimata: книга тем Kotlin и Android

Дата: 2026-11-17. Статус: утверждённый дизайн первой версии.

Приложение учит Kotlin и Android на уровне middle и выше. Это локальная книга из карточек: стартовый каталог уже лежит в базе, свою тему можно дописать. Сервис со списком тем будет отдельной задачей. Сейчас его нет, экраны ходят только в локальный репозиторий.

Название на лаунчере остаётся `Android Tutorial`. Тексты интерфейса на русском. Примеры кода на Kotlin.

## Решения

- Один Gradle-модуль `app`. Пакеты повторяют будущие модули: фича не импортирует другую фичу. Связывает их только `app`.
- Room — единственный источник тем. `TopicRepository` — единственная дверь к ним.
- У каждого экрана с логикой свой MVI: намерение, состояние, разовое событие. Внедрение зависимостей через Hilt.
- Material 3, своя бежевая схема «тихая бумага».
- Авторизация без проверки. Кнопка «Войти» всегда открывает книгу.
- «Изучать» и профиль — пустые страницы.
- Стартовые темы нельзя удалять и нельзя редактировать. Свою тему нельзя редактировать: её удаляют и создают заново.
- Разбор и пример кода обязательны и у каталога, и у своей темы.
- Категория `Kotlin` или `Android` у своей темы обязательна.
- Значок своей темы — аватар человека, не буква раздела.

## Внешний вид

Страница `#F6F0E6`, карточка `#FFFBF6`, чернила `#3C322A`, вторичный текст `#8A7768`. Заголовки — `FontFamily.Serif`. Основной текст — системный гротеск.

Цвет раздела не заливает книгу.

- Главная бежевая. У учебной карточки значок-буква: K на `#EFE7FB` / `#6D4AD4` или A на `#E3F3EA` / `#2F7D52`.
- Вкладка Kotlin: заголовок `#5B3CC4` и верхняя дымка `rgba(127, 82, 255, 0.16)`, которая сходит в бумагу. Карточки бумажные.
- Вкладка Android: заголовок `#246B45` и дымка `rgba(61, 155, 110, 0.18)`.
- Сердце в избранном залито `#3C9A62`. Снятое — контур `#3C322A` с непрозрачностью 28%. Оно остаётся нажимаемым.
- Пример кода лежит на плашке `#EFE4D6`, моноширинный, с горизонтальной прокруткой. Подсветки синтаксиса нет.
- Переход к теме: сдвиг справа и поворот около 8° по оси Y, 320 мс. Назад — обратный жест. Смена вкладок — короткое затухание около 150 мс, без перелистывания.

Аватар вверху справа — нейтральный контур человека. Он открывает профиль и на карточках не используется.

Своя тема получает круглый аватар человека. Фон круга красится категорией: фиолетовый для Kotlin, зелёный для Android. Буквы K или A на своей теме нет. На Главной свои и учебные карточки различаются формой значка, а раздел всё равно читается по цвету.

## Навигация

Одно activity. Старт — вход. «Войти» открывает обложку и снимает вход со стека.

Нижняя панель: Главная, Kotlin, Android, Изучать, Избранное. У каждой вкладки своё состояние прокрутки.

Поверх панели:

- Страница темы. Нижняя панель скрыта. Назад возвращает на ту же вкладку и то же место списка.
- Форма своей темы. Плюс только на Главной, Kotlin и Android.
- Профиль. Иконка справа вверху. Нижняя панель скрыта.

С Главной, Kotlin и Android открывается одна и та же страница темы. Фильтр вкладки задаёт, какой список её показал.

## Экраны

**Вход.** Поля «Логин» и «Пароль», кнопка «Войти». Содержимое полей ни на что не влияет. Ошибки нет.

**Список.** Карточка: значок слева сверху, название, краткое описание, сердце справа сверху. Нажатие на сердце меняет избранное и не открывает тему. Нажатие на остальную карточку открывает тему.

Главная перемешивает все темы при каждом входе на вкладку, включая свои. Пока пользователь остаётся на Главной, листает её или возвращается со страницы темы, порядок не меняется. Новый порядок появляется, когда он ушёл на другую вкладку и снова открыл Главную.

Kotlin показывает только Kotlin. Android — только Android. Сначала учебные темы в порядке каталога, затем свои по времени создания. Избранное показывает отмеченное тем же порядком внутри раздела: блок Kotlin, затем блок Android. Пустое избранное: «В книге пока нет закладок».

Свайп в сторону есть только у своей темы. Карточка сразу исчезает. Около четырёх секунд виден снэкбар «Отменить». Отмена возвращает тему с тем же id. Если не нажать, тема остаётся удалённой после перезапуска. Снэкбар живёт на обложке и не пропадает при смене вкладки. Уход процесса, пока снэкбар виден, оставляет тему удалённой.

**Своя тема.** Поля: название, краткое описание, разбор, пример кода, категория. Категория — две кнопки, Kotlin и Android. С вкладки Kotlin выбрана Kotlin. С вкладки Android выбрана Android. С Главной не выбрано ничего, пока пользователь не нажмёт.

Сохранение возможно, когда после обрезки пробелов все тексты непустые и категория выбрана. Иначе пустые поля и невыбранная категория подсвечиваются, запись в базу не уходит. Назад без сохранения выбрасывает черновик.

**Страница темы.** Значок по тем же правилам, название, сердце, разбор, пример кода. Если темы с таким id уже нет, экран закрывается.

**Изучать.** Текст: «Вопросы по темам появятся здесь».

**Профиль.** Текст: «Здесь будет видно, что ты уже разбирал».

## Данные

Таблица `topics` в базе `mathimata.db`, версия 1.

| Поле | Смысл |
|---|---|
| `id` | Ключ, autogenerate |
| `title` | Название |
| `summary` | Текст карточки |
| `body` | Разбор на странице |
| `codeSample` | Пример кода |
| `category` | `KOTLIN` или `ANDROID` |
| `isFavorite` | В избранном |
| `isBuiltIn` | Учебная тема каталога |
| `sortOrder` | Порядок учебной темы внутри раздела, 1…10 |
| `createdAt` | Время создания, у каталога время вставки |

Значок в базе не хранится. Его собирает интерфейс из `isBuiltIn` и `category`.

`onCreate` пустой базы вставляет 20 учебных тем один раз. Повторный запуск их не добавляет. Новые пункты каталога в следующей версии приложения придут отдельной миграцией, а не повторной вставкой.

Своя тема пишется с `isBuiltIn = false` и `sortOrder = 0`. Избранное можно менять и у учебной темы, и у своей.

```text
observeAll(): Flow<List<Topic>>
add(draft): сохраняет свою тему
deleteUserTopic(id): Boolean, удаляет только isBuiltIn = false и возвращает false, не бросая исключение, если темы нет или она учебная
restore(topic): вставляет ту же тему с прежним id
setFavorite(id, favorite)
```

Экраны получают модель `Topic`. Entity, Dao и Database остаются в `core/data`. Репозиторий не фильтрует и не перемешивает.

ViewModel списка сам делит поток. Для Kotlin и Android он оставляет учебные темы в порядке `sortOrder`, а свои ставит после них по `createdAt`. Избранное собирается так же, но двумя блоками: сначала Kotlin, затем Android. Для Главной он берёт уже собранный список всех тем и перемешивает его в памяти один раз на заход. Пока вкладка не покинута, повторные значения из Flow проходят через тот же порядок id.

## Каталог

`TopicSeed` копирует тексты ниже дословно. `summary` попадает на карточку, `body` и `codeSample` — на страницу темы. Примеры самодостаточны: по ним видно поведение, даже если соседние типы в приложении не объявлены.

### Kotlin

1. **Стирание типов и reified.** `sortOrder` 1.
   - summary: На JVM параметр типа стирается, а `reified` видит его в месте вызова.
   - body: На JVM параметр типа стирается до верхней границы. В рантайме список строк и список чисел выглядят одинаково, поэтому проверка `is List<String>` не компилируется. Обычная функция не может спросить `is T`. `inline` с `reified` подставляет конкретный тип туда, где функцию вызвали, и такая проверка становится обычной.
   - codeSample:

```kotlin
inline fun <reified T> List<*>.firstIs(): Boolean = firstOrNull() is T
```

2. **Дисперсия in и out.** `sortOrder` 2.
   - summary: `out` отдаёт значения наружу, `in` принимает их внутрь, изменяемая коллекция инвариантна.
   - body: Если тип только отдаёт значения, его можно читать как более общий. Если только принимает, в него можно передать более конкретное. `List` отдаёт элементы и объявлен как `out`. `MutableList` и читает, и пишет, поэтому звезда или другой аргумент типа туда не подставляются.
   - codeSample:

```kotlin
fun lengths(items: List<out CharSequence>): List<Int> = items.map { it.length }
```

3. **Structured concurrency.** `sortOrder` 3.
   - summary: Корутина живёт в scope: отмена родителя отменяет детей, scope дожидается их.
   - body: Корутину не запускают в пустоту. Она принадлежит scope, и отмена этого scope отменяет детей. `coroutineScope` ждёт все дочерние задачи. Если одна падает, остальные отменяются, а ошибка выходит из функции наружу.
   - codeSample:

```kotlin
suspend fun load(): Pair<String, String> = coroutineScope {
    val chapter = async { readChapter() }
    val notes = async { readNotes() }
    chapter.await() to notes.await()
}
```

4. **Кооперативная отмена.** `sortOrder` 4.
   - summary: Отмена срабатывает в точках, где корутина сама проверяет свой Job.
   - body: Отменённый Job сам не выдёргивает поток из чужого цикла. `delay`, `yield` и функции `kotlinx.coroutines` проверяют отмену сами. Свой долгий цикл остаётся живым, пока в нём нет `ensureActive()` или другой точки приостановки, которая смотрит на Job.
   - codeSample:

```kotlin
suspend fun poll() {
    while (true) {
        ensureActive()
        readPacket()
    }
}
```

5. **Dispatchers и withContext.** `sortOrder` 5.
   - summary: `withContext` переносит блок на другой диспетчер и возвращает результат обратно.
   - body: `Main` нужен интерфейсу, `Default` — вычислениям, `IO` — ожиданию файлов и сети. `withContext` выполняет блок в новом контексте. Результат блока возвращается туда, где функцию вызвали, без ручной передачи между потоками.
   - codeSample:

```kotlin
suspend fun parse(file: File): String = withContext(Dispatchers.IO) {
    file.readText()
}
```

6. **Общее изменяемое состояние.** `sortOrder` 6.
   - summary: Общий `var` либо живёт в одном потоке, либо закрыт `Mutex`.
   - body: Две корутины могут прочитать одно значение и записать его обратно, потеряв чужое изменение. Примитивный `var` этого не запрещает. Состояние держат в одном диспетчере или защищают критическую секцию. `Mutex` пропускает в секцию одну корутину и отпускает её без блокировки потока.
   - codeSample:

```kotlin
val mutex = Mutex()
var count = 0

suspend fun inc() {
    mutex.withLock { count++ }
}
```

7. **Flow, StateFlow, SharedFlow.** `sortOrder` 7.
   - summary: Холодный Flow считается заново, StateFlow хранит значение, SharedFlow раздаёт события.
   - body: Обычный Flow холодный: работа внутри `flow { }` начинается для каждого сборщика отдельно. StateFlow горячий и всегда помнит последнее значение, поэтому новый сборщик получает его сразу. SharedFlow тоже горячий, но предназначен для событий. Он не запускает источник сам, у него есть подписчики и настройка повтора.
   - codeSample:

```kotlin
fun ticks(): Flow<Int> = flow {
    var n = 0
    while (true) {
        emit(n++)
        delay(1_000)
    }
}
```

8. **Исключения и supervisorScope.** `sortOrder` 8.
   - summary: `supervisorScope` не отменяет соседей, но ошибку ребёнка всё равно нужно обработать.
   - body: В `coroutineScope` падение одной дочерней корутины отменяет остальных, и функция завершается с ошибкой. `supervisorScope` изолирует это падение: соседние задачи продолжаются. Ошибка ребёнка при этом не исчезает. Её ловят вокруг конкретной задачи или отдают `CoroutineExceptionHandler`, иначе она уходит обработчику контекста.
   - codeSample:

```kotlin
suspend fun loadIndependently() = supervisorScope {
    launch { risky() }
    launch { steady() }
}
```

9. **Continuation.** `sortOrder` 9.
   - summary: `suspend`-функция останавливается на точке приостановки и продолжается позже.
   - body: Приостановка не блокирует поток. Компилятор превращает `suspend`-функцию в состояние, которое можно остановить и снова вызвать. После `delay` продолжение может пойти на другом потоке, если так устроен контекст. В коде это выглядит как обычный последовательный вызов.
   - codeSample:

```kotlin
suspend fun step() {
    work()
    delay(100)
    work()
}
```

10. **Делегирование.** `sortOrder` 10.
    - summary: `by` передаёт интерфейс другой реализации, а у свойства заменяет ручной геттер.
    - body: Делегирование интерфейса пересылает его методы выбранному объекту. Класс остаётся этим интерфейсом и добавляет только своё. Делегированное свойство прячет хранение и первый расчёт. `lazy` считает значение при первом чтении, `observable` узнаёт о каждой новой записи.
    - codeSample:

```kotlin
interface Store {
    fun read(): String
}

class Repo(private val store: Store) : Store by store
```

### Android

1. **Ментальная модель Compose.** `sortOrder` 1.
   - summary: Экран — функция состояния. Новый state описывает кадр заново.
   - body: Composable описывает, что должно быть на экране при текущем состоянии. При новом state функция выполняется снова, и дерево сравнивается с предыдущим. Виджеты не хранят скрытые изменения, которые обошли состояние. То, что должно сохраниться, лежит в state, а не в полях вью.
   - codeSample:

```kotlin
@Composable
fun TitleCard(title: String) {
    Text(title)
}
```

2. **Рекомпозиция и стабильность.** `sortOrder` 2.
   - summary: Заново выполняется участок, прочитавший новое состояние. Стабильные параметры позволяют пропуск.
   - body: Compose запоминает, какие composable прочитали изменившееся состояние, и вызывает их снова. Сосед, который это состояние не читал, может быть пропущен. Пропуск возможен, когда параметры сравнимы и не изменились. Нестабильный параметр заставляет Compose перепроверять поддерево чаще.
   - codeSample:

```kotlin
@Composable
fun Page(title: String, count: Int) {
    Header(title)
    Counter(count)
}
```

3. **Три фазы кадра.** `sortOrder` 3.
   - summary: Кадр проходит Composition, Layout и Drawing. Состояние читают в нужной фазе.
   - body: Composition строит дерево функций. Layout измеряет детей и раскладывает их. Drawing рисует уже размещённое. Чтение состояния во время композиции связывает его с пересборкой дерева. Смещение, которое нужно только при размещении, читают в лямбде layout, и тогда изменение не пересобирает composable заново.
   - codeSample:

```kotlin
Modifier.offset { IntOffset(x.roundToPx(), 0) }
```

4. **Жизненный цикл composable.** `sortOrder` 4.
   - summary: Composable входит в композицию и выходит из неё. `DisposableEffect` снимает работу на выходе.
   - body: Вызов composable оставляет его в дереве, пока родитель продолжает его вызывать. Когда вызов исчез или сменился ключ, composable выходит из композиции. `DisposableEffect` запускает подписку на входе и обязан отпустить её в `onDispose`. Иначе слушатель переживёт экран, которого уже нет.
   - codeSample:

```kotlin
DisposableEffect(player) {
    player.start()
    onDispose { player.stop() }
}
```

5. **Побочные эффекты.** `sortOrder` 5.
   - summary: `LaunchedEffect` живёт вместе с композицией и ключом. Из тела composable эффект не запускают.
   - body: Тело composable может выполниться много раз за кадр и при каждой рекомпозиции. Сетевой запрос, запущенный прямо оттуда, повторится вместе с ним. `LaunchedEffect` запускает корутину, пока composable в композиции, и отменяет её на выходе. Новый ключ отменяет старую корутину и запускает новую.
   - codeSample:

```kotlin
LaunchedEffect(topicId) {
    repository.load(topicId)
}
```

6. **Где хранить состояние.** `sortOrder` 6.
   - summary: `remember` живёт в композиции, `rememberSaveable` переживает поворот, ViewModel хранит состояние экрана.
   - body: `remember` возвращает то же значение, пока composable в дереве. Поворот Activity создаёт композицию заново, и такое значение пропадает. `rememberSaveable` кладёт то, что можно сохранить, в механизм saved instance state. Данные экрана и загрузка живут во ViewModel: он остаётся при пересоздании интерфейса.
   - codeSample:

```kotlin
val draft = rememberSaveable { mutableStateOf("") }
```

7. **Смерть процесса.** `sortOrder` 7.
   - summary: Процесс могут убить. `SavedStateHandle` возвращает минимум для восстановления экрана.
   - body: ViewModel не переживает смерть процесса. Система может сохранить небольшой набор, который приложение само записало. `SavedStateHandle` читает этот набор при новом создании ViewModel. Туда кладут id открытой темы или другой ключ, без которого экран нельзя собрать заново.
   - codeSample:

```kotlin
class ReaderViewModel(saved: SavedStateHandle) : ViewModel() {
    val topicId = saved.getStateFlow("topicId", 0L)
}
```

8. **Смена конфигурации.** `sortOrder` 8.
   - summary: При повороте Activity создаётся заново, ViewModel того же scope остаётся.
   - body: Смена конфигурации уничтожает Activity и создаёт новую. Scope ViewModel, привязанный к владельцу экрана, при этом сохраняется. Новая композиция читает уже загруженное состояние и не повторяет запрос только потому, что повернулся экран.
   - codeSample:

```kotlin
@HiltViewModel
class TopicsViewModel @Inject constructor(
    private val repository: TopicRepository
) : ViewModel()
```

9. **Главный поток.** `sortOrder` 9.
   - summary: Композиция идёт на main. В кадр попадает готовое состояние, а не долгая работа.
   - body: Чтение базы, разбор файла и сеть на главном потоке задерживают кадр. Такую работу запускают в корутине на подходящем диспетчере. Composable читает уже полученное состояние. Пока результата нет, экран показывает прежнее состояние или пометку ожидания, а не считает работу внутри композиции.
   - codeSample:

```kotlin
viewModelScope.launch {
    _state.value = repository.load()
}
```

10. **Сбор потока в UI.** `sortOrder` 10.
    - summary: `collectAsStateWithLifecycle` собирает Flow, пока экран виден, и останавливает сборку в фоне.
    - body: Обычный `collect` в композиции может держать работу, когда Activity уже на паузе. `collectAsStateWithLifecycle` привязывает сборку к жизненному циклу и по умолчанию собирает поток не ниже `STARTED`. Уход экрана в фон отменяет сборку. Возврат запускает её снова.
    - codeSample:

```kotlin
val topics by repository.observeAll().collectAsStateWithLifecycle()
```

## Ошибки

Отказ базы при сохранении, закладке или удалении не меняет показанный список. Внизу появляется «Не получилось сохранить». Повтор доступен тем же действием.

`deleteUserTopic` для учебной или неизвестной темы возвращает `false` и ничего не стирает. Интерфейс не показывает свайп у учебной карточки.

Пустая форма не считается ошибкой базы. Это состояние формы.

## Тесты

Инструментальные тесты репозитория на in-memory Room:

- первый запуск вставляет 20 тем, повторное открытие той же базы не добавляет строки;
- своя тема добавляется с выбранной категорией и `isBuiltIn = false`;
- удаление своей темы и `restore` возвращают тот же id;
- `deleteUserTopic` учебной темы возвращает `false`, таблица не меняется;
- закладка переключается у обоих видов тем.

JVM-тесты ViewModel на поддельном репозитории:

- фильтр Kotlin и Android оставляет темы раздела: учебные по `sortOrder`, свои после них по `createdAt`. Избранное ставит блок Kotlin перед блоком Android;
- Главная один раз передаёт список в переданный `Random` и при новых значениях Flow сохраняет порядок этих id;
- новый заход на Главную создаёт новый `Random` и перемешивает заново;
- свайп своей темы убирает её и публикует «Отменить»;
- отмена вызывает `restore`;
- свайп учебной темы не вызывает удаление;
- форма без категории или с пустым разбором не вызывает `add` и помечает поле.
